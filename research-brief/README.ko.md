# research-brief

[English](README.md) · [← 메인으로](../README.ko.md)

기술 질문을 그 답을 실제로 정하는 출처에서 확인하고, 반년 뒤에도 다시 검증할 수
있는 조사 문서를 남깁니다.

## 무엇이 다른가요?

조사가 쓸모없어지는 경로는 두 가지입니다. 하나는 근거 없이 자신 있게 쓴 문장이고,
다른 하나는 읽을 때는 맞았지만 지금은 틀린 출처인데 문서만 봐서는 그걸 알 수 없는
경우입니다.

`research-brief`는 주장마다 출처 정보를 함께 달아서 두 문제를 막습니다.

- **출처 등급.** T1은 명세, 공식 레퍼런스, 1차 소스 코드입니다. T2는 공식 변경
  기록이나 관리자 글 같은 1차측 2차 자료입니다. T3은 커뮤니티 자료로, 확인되지
  않았다는 표시 없이는 쓸 수 없습니다. T3 주장은 답이 아니라 T1 출처로 가는
  단서입니다.
- **버전 고정.** 주장마다 어느 버전이나 날짜를 기준으로 확인했는지 적습니다.
  "최신"이 아니라 `4.2.1`입니다. 오래된 문서인지 틀린 문서인지 구분하려면 이
  정보가 필요하고, 둘은 대응 방법이 다릅니다.
- **모순 기록.** 출처 두 개가 어긋나면 둘 다 남기고, 어느 쪽을 택했는지와 그 이유를
  적습니다. 하나를 지우면 조사에서 가장 값진 발견을 버리는 셈입니다. T1 출처끼리
  어긋나는 지점이 바로 찾던 버그가 있는 자리인 경우가 많습니다.
- **남은 의문은 필수.** 비어 있다면 왜 비었는지 한 줄로 적어야 합니다. 아무 의문도
  없고 설명도 없는 문서는 질문을 그만둔 문서입니다.

답이 먼저, 근거가 나중입니다. 결론과 확신 수준을 맨 위에 둡니다. 끝까지 읽어야
답이 나오는 문서는 읽히지 않습니다.

## 설치 방법

전역 설치:

```bash
npx skills add -y -g chann/skills --skill research-brief
```

현재 프로젝트에 설치:

```bash
npx skills add chann/skills --skill research-brief
```

## 사용법

| Claude Code | Codex | 하는 일 |
|---|---|---|
| `/research-brief [질문]` | `$research-brief [질문]` | 1차 출처로 질문에 답하고 `.research/`에 근거를 붙인 문서를 남김 |

예시:

```text
/research-brief 우리 HTTP 클라이언트가 기본으로 재시도하는지 확인해줘
$research-brief 이 API는 커서가 만료되면 무엇을 반환해?
/research-brief 이 라이브러리 기본 타임아웃 몇 초인지 공식 문서로 확인해줘
```

플랫폼이 백그라운드 에이전트를 지원하면 읽는 작업을 넘겨서 사용자가 계속 작업할
수 있게 합니다. 이때 주제만 넘기지 않고 질문, 출처 등급, 출력 형식까지 함께
넘깁니다.

## 문서 구성

```markdown
# <질문>
## Bottom line          ← 결론과 확신 수준
## Claims               ← 주장 | 출처 | 등급 | 확인 기준 | 확신 수준
## Detail
## Contradictions
## Open questions        ← 필수
## Sources
```

## 하지 않는 일

- T3 커뮤니티 주장을 사실처럼 쓰기
- 출처를 열지 않고 검색 결과 요약을 근거로 쓰기
- 버전이나 날짜 없이 주장 적기
- 한쪽을 지워서 모순을 없애기
- 빈칸을 그럴듯한 답으로 채우기
- 범위 안의 질문이 답을 못 찾았는데 완료라고 말하기
